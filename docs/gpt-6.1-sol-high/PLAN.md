# 380 个设计的网页生成计划

当前轮次上限：用户要求先完成清单前 200 项后停止。调度器不得启动编号大于 200 的设计。前 200 项的网页、截图、源码推送和群通知全部完成后，管理会话核验 Git 远端及全部交付，再暂停任务；其余 180 项保留台账，等待用户后续指示。完整清单仍为 380 项。

状态：用户已授权执行。每个设计使用全新独立会话；总并发不超过 7（包含管理会话）。前三个生成会话已启动。

## 目标与输入

- 380 个设计各生成一个可运行网页，使用 GPT‑6.1 Sol，推理强度 High。
- 主提示词采用画廊当前的默认版本，由 `data/catalog-text-index.json` 指定；601 个文本版本不全部展开。
- 已建立 `inventory.md`、`inventory.csv` 和 `manifest.json`。清单记录设计 ID、分类、主提示词路径、版本 ID、原文 SHA‑256、来源、预览资源和状态。
- 提示词保持原文。执行说明单独保存，只约定输出目录、构建和验收要求，避免改变设计要求。
- 目前只验证了输入文件和目录数据，尚未逐条评估全部提示词中的外部素材、运行依赖与实现难度。

## 会话与进度管理

本会话作为总管理入口，负责分派、查看结果、安排修复和向用户汇报。建议每个设计使用一个独立生成会话，避免不同设计相互影响；初始并发 3 个。

每个任务明确设置 `gpt-6.1-sol` 和 `model_reasoning_effort=high`，记录实际会话配置与会话 ID。若运行记录不能证明设置正确，先标为待核实，不计入验收完成。

所有状态写入台账，不只保留在聊天上下文里。恢复工作时先读取台账和实际产物，再决定继续、重试或验收。各生成会话只写自己的目录；总台账由管理端统一更新。

建议状态：未开始 → 排队 → 生成中 → 待验收 → 已验收；另外记录待修复、阻塞。分别统计代码产出数和验收通过数。失败保留原日志，修复有次数上限，避免无限重跑。

管理会话分批创建全新任务；同一设计可在原独立会话中修复，禁止把新设计交给旧会话。新任务默认 3 并发，最多 6 个生成会话，加管理会话共 7 个。

## 产物组织

实际源码目录为仓库内 `generated/gpt-6.1-sol-high/<design-id>/`；每项源码和截图需推送 origin/main，node_modules 不入库。公开成果入口为 https://tool.luo-xd.com/motionsites-results/ ，单项路径为该入口下的设计 ID。

每个设计保留：

- 原始提示词快照、来源信息和执行说明。
- 网页源代码、必要依赖清单及锁文件、运行说明。
- 构建后的静态网页，优先支持通过普通 HTTP 服务访问。
- 桌面和手机截图、检查报告、素材替代记录。
- 会话 ID、模型配置、开始/结束时间、尝试次数和实际可获得的用量记录。

技术栈优先遵循原提示词：要求 React、Tailwind、GSAP 等就按要求实现；未指定时选择简单可靠的方案。不同作品可使用不同源码结构，但尽量统一构建产物的预览方式。确需服务端的作品单独标记运行需求。

图片、视频优先使用提示词指定资源。原预览截图仅作视觉参照，不能作为整页背景冒充实现。外链失效时记录原因和替代方案；不静默换素材。

超出 GitHub 单文件限制的原素材保留原始字节，以每块小于 50 MiB 的文件、原文件及分块 SHA-256 清单存入项目 `asset-chunks/`。构建和开发启动前自动校验并还原，忽略还原后的超限文件及 dist；独立验收须验证已提交分块能逐字节重建实际使用的原素材。发布前检查待提交文件大小，避免超限提交阻塞后续作品。Blog Showcase 首次采用此方式，视频未经转码。

## 分阶段推进

### 第一阶段：3 个试做

建议先做画廊前三项，确认从输入到构建、预览和验收的完整流程：

| 设计 | 主要验证点 |
| --- | --- |
| Dreamcore Landing | 长提示词、滚动场景切换与排版 |
| Bold Studio | 全屏视频、移动端菜单与入场动画 |
| Interactive Discovery | 鼠标跟随遮罩、图像与响应式布局 |

完成后提供 3 个预览、截图、偏差说明与真实耗时/可获得的用量。管理会话完成验收后继续推进，不额外等待逐批批准。

### 第二阶段：补足至 15 个

再选 12 个，覆盖浅色页面、表单、定价、仪表盘、3D/Shader、无预览设计，以及不同提示词来源。这一阶段重点发现通用流程之外的问题，不把前 3 个的表现直接推断到全库。

根据前 15 个的实际情况估算剩余工作量、存储需求和可获得的用量数据。当前不承诺固定工期或虚构费用。

### 第三阶段：剩余 365 个

建议每批 10–20 个，初始并发仍为 3；根据服务器负载、模型额度和失败率调整。每批报告已生成、已验收、待修复、阻塞和未开始数量，以及可预览的成果。

### 第四阶段：展示与交付

建立统一结果索引，能从设计 ID 找到网页、源码、截图和检查报告。用户已要求部署到 tool.luo-xd.com/motionsites-results/；索引列出原提示词名称、网页入口、预览截图和原提示词对应关系。每项完成后，向 /codex/ 服务的群聊发送项目名称及访问地址，记录消息 ID。

## 验收标准

1. 能按说明安装和构建，并通过 HTTP 打开实际网页。
2. 在 1440×1000 桌面与 390×844 手机视口检查布局；无影响使用的横向溢出、遮挡或无法关闭的菜单。
3. 核对原提示词的主要布局、配色、字体层级、内容和动画/交互要求。无参考预览的设计以提示词为准。
4. 关键按钮、菜单、切换、表单等实际可操作；演示行为如实说明，不虚构后端提交成功。
5. 记录浏览器脚本错误、资源失败和字体/视频加载问题；影响主要内容的问题必须修复或标为阻塞。
6. 每个设计保存截图和检查报告。截图成功只代表检查的一部分，不自动等同于设计质量通过。

浏览器基础检查可以自动化；设计符合度和动画效果另行查看。先在试做阶段验证检查工具，再用于批量验收。

## 含服务端功能的项目

OYLA 按原提示词运行 Express 生产服务，容器为 `motionsites-oyla`，使用 `scripts/generation/deploy-oyla.py` 和对应 Dockerfile 重建。静态页面由结果站点提供，项目路径下的 `/api/higgsfield-video` 转发至该容器；两个指定分享链接均需通过公网 API 验证。容器独立安装锁文件中的生产依赖，不依赖生成工作目录的 node_modules。

Glitch Pulse 使用 `scripts/generation/deploy-glitch-pulse.py` 和对应 Dockerfile 运行原始 `server.ts`，生产环境容器为 `motionsites-glitch-pulse`。项目页面和资源转发至该 Express 服务，`preview/` 由静态发布目录提供；验收需核对容器健康、生产环境、实际启动命令、原始服务器文件与公网 HTML，并确认截图可访问。

第 197 项 `pulse-3d` 的提示词仅要求安装 Express 等依赖，并明确页面为无持久化的展示页面；原文没有要求启动 Express 服务。按实际生成的应用结构部署和验收，不额外添加服务端功能。每个项目仍由其原有独立会话生成；部署由管理会话处理。

第 180 项 `nimbus-grid` 明确要求嵌入 `https://fragcoord.xyz/embed/c6zisyc6` 的动画着色器。其独立项目路径的 CSP 仅额外允许 `https://fragcoord.xyz` 作为 iframe 来源；成果索引与其他项目继续沿用各自策略。上线后仍须检查实际 iframe 加载和浏览器结果。
